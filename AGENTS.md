# Next Alphabet project guidance

## Build series documentation style

Use the existing Build episode pages as the visual and editorial reference for future documentation.

- Prefer a restrained, editorial layout built with typography, hierarchy, and generous whitespace.
- Keep pages simple, clear, useful, and consistent with the surrounding Build UI.
- Avoid dashboard-style stat cards, promotional hero cards, dense tables, two-column data grids, and excessive containers.
- Avoid horizontal divider lines between repeated resources or facts when spacing can separate them.
- Present factual summaries as short natural-language paragraphs when that reads more cleanly than a table.
- Show resource links as quiet single-row actions with the title and supporting context on the left and a right-facing chevron on the far right.
- Use subtle rounded hover backgrounds for link rows; do not add permanent boxes unless the action genuinely benefits from one.
- Keep action content on one aligned row when space allows, including the Instagram episode link.
- Emphasize the most useful user outcome in the copy. For training or certification content, lead with what people can learn and do, not eligibility restrictions.
- Keep caveats accurate but visually and editorially secondary unless they are safety-critical.
- Reuse the established episode typography, spacing, icon weight, muted colors, and content width.
- When uncertain, choose the quieter and more readable option.

## Copyable setup prompts

- When a setup prompt mentions a tool, package, repository, MCP server, plugin, or integration, include the relevant official source URLs inside the copyable prompt itself.
- Do not rely on resource links elsewhere on the page to identify what the prompt should install or configure.
- Prefer the official repository and the most relevant official setup documentation. Keep the surrounding explanation short and tidy.
